# 密钥扩展算法安全分析
**总体结论：没有“一击致命”的破绽，但确实存在真实的问题**——一个可证明的代数结构缺陷（注入层差分抵消）、一个完全可逆性（轮密钥泄露 = 主密钥泄露）、若干未分析的 related-key 攻击面，以及一批工程隐患（其中一个意味着当前代码事实上已处于不一致状态）。也有一个好消息：**不存在等价密钥**。
---
## 一、可证明的结构缺陷：注入层的确定性差分抵消（核心发现）
设 `C` 为 `key_constant` 的逐字节展开，镜像位置 `m = j ⊕ 0x10`。进入第一轮 ARX 之前，第 j 字节的状态是：
```
S[j] = (K[j] ⊕ C[j]) + K[j] + swap(K[m])   (mod 256)
```
注意：**同一个密钥字节 K[j] 以两种方式进入了同一字节**——XOR 域（`K[j] ⊕ C[j]`）和 ADD 域（`M[j] = K[j] + swap(K[m])`）。
单比特翻转 `δ = 2^k` 满足 `(x ⊕ δ) − x = ±2^k`（精确成立，无进位串扰）。于是：
```
ΔS[j] = σ₁·2^k + σ₂·2^k  (mod 256)，σ ∈ {+1, −1}
```
* **k = 7**：`±2^7 ± 2^7 ∈ {0, ±2^8} ≡ 0 (mod 256)` → **无条件抵消**
* **k < 7**：`σ₁ = σ₂ ⟺ bit_k(C[j]) = 0`。即 **`bit_k(C[j]) = 1` 时恒抵消**；否则差分变为 `±2^{k+1}`（翻倍到相邻高位）
**推论：**
1. `S[j]` **完全不依赖** `K[j]` 的最高位 bit 7。
2. 对 `C[j]` 中为 1 的每个比特位（逐字节 2~7 个不等，约一半），`S[j]` 同样不依赖 `K[j]` 的对应位。**哪些位抵消由公开常数唯一决定，攻击者完全可预测。**
3. 差分没有消失，而是以 `±2^{k±4}` 的幅度“位移”到镜像字节 m（swap 把 bit k 移到 k±4）。
**数值验证**：`K[j]=0x12, C[j]=0x34, K[m]=0xAB`：
`S = 0x26 + 0x12 + 0xBA = 0xF2`；翻转 bit7 后 `K'[j]=0x92`：
`S' = 0xA6 + 0x92 + 0xBA = 0xF2` —— 逐字节完全相同。
**影响评估**：单比特 related-key 差分在进入 ARX 之前被压缩成镜像位置上的单字节小幅度差分。8 轮 ARX 大概率会将其扩散（未经实验验证），所以**不能断言直接可利用**；但这是教科书式的 related-key 差分入口结构——非预期的代数结构，应当修掉。
**根因与修法**：同一密钥字节未经混合，同时以 XOR 域和 ADD 域叠加到同一字节上。可选修法：
* 注入材料先过变换（如注入 `rotl(M, 8·iter)`）；
* 注入改用 XOR（与白化同域）；
* 让 mix 步携带 iter 相关常数（目前 mix 完全不区分 4 次迭代）。

## 二、调度完全可逆：轮密钥泄露 = 主密钥泄露
ARX 轮是可逆的：按 `i = 7→0` 逆序处理——i=7 的邻居 (0,1,2) 此刻已是新值且不再变化；i=6 的 dk[7] 已由上一步还原；以此类推，逐字相减即可。因此整个调度可被几行代数完全逆推：
```
S₀_pre = ARX₀⁻¹(RK[0])
M      = ARX₁⁻¹(RK[1]) ⊖ RK[0]    （逐字节 mod 256 减法）
K      = (S₀_pre ⊖ M) ⊕ C          （逐字节）
```
**任意两个相邻的 32 字节轮密钥块 ⇒ 完整 256 位主密钥，运算量微秒级。** 若威胁模型包含进程内存/栈泄露（崩溃转储、Heartbleed 式漏洞），轮密钥与主密钥一损俱损，调度没有提供任何加固。
同一个公式也是好消息的证明：它对任意调度输出都成立，故调度是 `K → RK` 的**单射**——**两个不同密钥不可能产生相同的轮密钥序列，不存在等价密钥。**
（公平地说：AES 的调度同样可从轮密钥逆推主密钥，这在业界属“正常”，前提是轮密钥同样保密。这里的问题是零额外代价、且对部分泄露零容忍。）

## 三、未证明但值得警惕的攻击面
* **4 次注入完全相同**：ΔM 以已知位置、已知幅度（j 处 ±2^k，镜像处 ±2^{k±4}）在全部 4 个注入点重复注入——攻击者可把它当作可控差分注入器。
* **ARX 串行就地更新**：词 0–4 只用旧值，词 5–7 混入已更新的值——非标准结构，词间扩散不对称，且现成的 ARX 分析工具难以直接套用。
* **每块仅 8 轮 ARX**：词级扩散 3 轮即满，但位级扩散（尤其低位——加法进位只向上传播）依赖旋转兜底，建议实测雪崩。
* **常数无来源说明**（"nothing up my sleeve" 缺失）：`key_constant` 无法审计；`golden·n (n=1..32)` 序列本身没问题（互异、非零）。
* 固定旋转集合与 ChaCha 同类，不算缺陷；`shift_n[3]=8` 字节对齐、`shift_n[4]=2` 偏小，影响轻微。

## 四、工程与健壮性问题（按实际影响排序）
1. ~~**头文件与实现已经不匹配**：`op4_key_extension.hh` 仍声明 `key_extension_step1/2/3`，而 `.cc` 定义的是改名后的三个函数——这组声明现在悬空，任何其他 TU 一旦调用即链接错误。建议 detail 函数直接移入 `.cc` 匿名命名空间，头文件只暴露 `key_extension`。~~
2. **循环次数的隐式耦合**：`i < nr/2` 的真实语义是“轮密钥块数 = rks/ks”。当前 `ks = 2·bl` 时恰好成立；一旦参数变动（如 ks=16 或 nr 为奇数），`round_key` 尾部将**未初始化**——真实的潜伏漏洞。改为 `rks / ks` 并加 static_assert。
3. **常数数组尺寸与 ks 硬耦合**：ks 改为 64 时 `shift_n[8]`/`key_constant[8]` 会越界读。加 `static_assert(sizeof(shift_n)/4 == op4::ks/4)`。
4. **`dk[8]` 持有完整密钥态但出作用域不清零**（`flush_key` 清了，`dk` 漏了）。
5. **死代码**：`{0}` 初始化 + `memcpy(flush_key, key, ks)` 随即被 `xor_key_constants` 从 origin_key 全量覆盖。若本意是“对当前状态做 in-place 白化”，实现读的是 origin_key，与意图不符——值得确认。
6. **`load32le`/`pack32le` 的 `if constexpr` 链无兜底**：混合字节序平台上 load 返回 0、pack 不写任何字节，静默全错。加 `static_assert` 限定 LE/BE。
7. `rotl32` 在 n=0 时 `x >> 32` 是 UB（此处未触发）；`rotl8/rotr8` 的 u32 参数与 8 位旋转语义不一致。
8. `SecureZeroMemory` 与 Win32 宏同名，同时引入 windows.h 会冲突，建议改名。
9. **未定义的重叠契约**：`round_key` 与 `key` 不允许重叠（mix 每轮迭代都读 origin_key，而 round_key 持续写入），应文档化或断言。
10. `nk = 4` 未使用且与 `ks/4 = 8` 不符；`rks = bl·nr` 的 16 字节/轮粒度与 32 字节调度块（每块覆盖两轮）的对应关系建议注释说明。

## 五、建议的验证实验
* **雪崩测试**：翻转每个密钥位，统计各 RK 块的输出翻转率（应 ≈50%），重点观察 bit 7 与低位。
* **Related-key 实验**：枚举全部 256 个单比特 ΔK，测 ΔRK[t] 的汉明重量分布是否偏离随机。
* **回归测试**：把第二节的逆推公式实现为单元测试——既验证可逆性结论，也充当实现一致性测试。
---
**总评**：作为学习型/自研设计，调度“骨架”尚可（单射、轮常数互异、常数时间、无越界），但注入层抵消结构是必须修的实质缺陷；若目标是实际部署，建议直接采用经过审计的 KDF（HKDF/BLAKE2/SHA-3 派生轮密钥）或成熟 ARX 调度，而非继续加固此结构。
